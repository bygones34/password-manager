# ADR-002: Cryptographic Vault Format, Key Hierarchy, and AEAD Nonce Policy

* **Status:** Accepted
* **Date:** 2026-10-10
* **Milestone:** M1 (Secure Vault Core — M1.1)
* **Decision Makers:** Architecture & Security Team
* **Related Documents:** `THREAT_MODEL.md`, `VAULT_FORMAT.md`, `ADR-003`, `SECURITY_TEST_MATRIX.md`

---

## 1. Context

Operating locally on Windows 11, `PasswordManager` requires a cryptographic architecture capable of protecting credentials, account metadata, and vault integrity even if the database is stolen or tampered with at rest.

Key architectural and security requirements include:
1. **Encryption Primitive:** Modern, standardized, independently audited, and hardware-accelerated Authenticated Encryption with Associated Data (AEAD).
2. **Key Hierarchy & Separation:** When the user changes their master password, thousands of records should not need re-encryption; password rotation must be atomic and efficient. Records and manifests must not share an encryption key; cryptographic separation of duties is required.
3. **Context Binding:** An attacker moving a record to another vault (cross-vault injection) or swapping records within the same vault (substitution/swap) must be prevented at the AEAD layer.
4. **Nonce Management:** Nonce reuse under the same key in AEAD algorithms catastrophically breaks confidentiality and integrity. A sound nonce policy is mandatory.

---

## 2. Decision

### 2.1. AEAD Primitive: AES-256-GCM
**AES-256-GCM** was selected for vault header wrapping, manifests, and record envelopes:
* 256-bit key length,
* 96-bit (12-byte) nonce,
* 128-bit (16-byte) authentication tag.
* Implemented via .NET 10 `System.Security.Cryptography.AesGcm`, utilizing native AES-NI and CLMUL instruction sets on modern x64 processors for high throughput and constant-time execution.

### 2.2. Two-Tier Key Architecture & HKDF-SHA-256
A two-tier hierarchy is implemented rather than encrypting data directly with the master password or KEK:
1. **KEK (Key Encryption Key):** Ephemeral 256-bit key derived from master password and CSPRNG Salt via Argon2id.
2. **Vault Root Key:** Independent 256-bit primary key generated via CSPRNG during vault creation, stored wrapped with KEK using AES-256-GCM (`WrappedRootKey`).
3. **Sub-Key Derivation (HKDF-SHA-256):** `RootKey` never encrypts records directly. RFC 5869 `HKDF-Expand` derives dedicated sub-keys:
   - `RecordKey`: `HKDF-Expand(RootKey, info = "PWMV1-RECORD-KEY" || VaultId, L = 32)`
   - `ManifestKey`: `HKDF-Expand(RootKey, info = "PWMV1-MANIFEST-KEY" || VaultId, L = 32)`

### 2.3. Master Password Rotation (Key Re-Wrap)
Master password changes do not require re-encrypting records. The existing `RootKey` is re-wrapped using the new KEK (derived from the new password and fresh salt) and updated in `VaultHeader`. This operation completes atomically in $O(1)$ time.

### 2.4. 96-Bit CSPRNG Nonce Policy
* For each encryption operation, a 96-bit random nonce is generated using a **Cryptographically Secure Pseudo-Random Number Generator (CSPRNG — `RandomNumberGenerator.Fill`)**.
* Counter-based deterministic approaches risk catastrophic nonce reuse if state synchronization is lost across backups, crashes, or multi-threaded scenarios.
* Under the birthday bound, generating random 96-bit nonces under a single key provides a collision probability of $< 2^{-32}$ up to $2^{32}$ (~4 billion) encryptions.

### 2.5. Canonical Binary AAD (Additional Authenticated Data)
Encrypted envelopes are cryptographically bound to their context via canonical binary AAD:
* **Key Wrap AAD:** Header magic, format version, VaultId, KDF ID, and Argon2id parameters.
* **Record AAD:** $\text{VaultId (16B)} \mathbin{\Vert} \text{RecordId (16B)} \mathbin{\Vert} \text{EnvelopeVersion (4B)} \mathbin{\Vert} \text{UTF8}("\text{PWMV1-RECORD}")$.
* **Manifest AAD:** $\text{VaultId (16B)} \mathbin{\Vert} \text{EnvelopeVersion (4B)} \mathbin{\Vert} \text{UTF8}("\text{PWMV1-MANIFEST}")$.

## 3. Alternatives Considered

1. **Alternative 1: ChaCha20-Poly1305**
   * *Pros:* Secure, faster on CPUs without hardware AES acceleration.
   * *Cons:* Our primary target is modern Windows 11 x64 systems where AES-NI hardware instructions make AES-GCM significantly more energy and CPU efficient.
   * *Outcome:* AES-256-GCM selected.

2. **Alternative 2: Single KEK Directly Encrypting Records**
   * *Pros:* Simpler architecture, fewer derivation steps.
   * *Cons:* Changing the master password would require decrypting and re-encrypting every record in the vault. If a crash or power failure occurs mid-operation, risk of catastrophic data loss is high.
   * *Outcome:* Two-tier KEK / RootKey architecture selected.

3. **Alternative 3: Counter-Based (Sequential) Nonces**
   * *Pros:* Avoids the birthday bound, theoretical $2^{96}$ capacity.
   * *Cons:* Backups, snapshots, or process crashes can rewind the counter, leading to deterministic nonce reuse. Stateless random nonces protect against reuse across restores and replays.
   * *Outcome:* CSPRNG random 96-bit nonces selected.

---

## 4. Security & Architectural Outcomes

* **Integrity Guarantee:** Any single-bit alteration in database ciphertext causes AEAD verification to fail closed.
* **Vault Isolation:** Encrypted records from one vault cannot be decrypted in another (`VaultId` mismatch fails AAD verification).
* **Record Isolation:** Record substitution within a vault is prevented by `RecordId` AAD binding.
* **Performance:** Hardware-accelerated AES-GCM decrypts and encrypts records in microseconds; computational latency is intentionally concentrated in Argon2id KDF.
